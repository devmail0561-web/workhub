## Verdict exécutif

**Le socle est sérieux, E1 est fonctionnel, mais le projet n'est pas prêt pour une exposition publique ou une production.** Cinq constats **Élevés** touchent directement la sécurité ou la disponibilité :

1. le verrouillage de connexion peut bloquer **tous les utilisateurs web** à cause du proxy ;
2. un **jeton d'intégration reste valide après désactivation de son propriétaire** ;
3. les **secrets par défaut** de `.env.example` sont acceptés et le mode production n'est pas réellement appliqué ;
4. les **commits après réponse HTTP** peuvent renvoyer un succès mensonger sur un échec de révocation/logout ;
5. le login public permet un **DoS non authentifié par Argon2** et la limitation n'est pas atomique.

E1-04/E1-05 sont livrés et testés, mais **la DoD complète n'est pas satisfaite** : l'audit des écritures d'intégration (E1-08) manque.

## Constats Élevés

### H-01 — Le verrouillage de connexion peut bloquer tous les clients web

**Preuves**

- `frontend/nginx.conf:22` proxifie `/api` vers l'API.
- `frontend/nginx.conf:26` transmet `X-Forwarded-For`, mais l'API ne fait pas confiance à ces en-têtes.
- `backend/Dockerfile:25` lance Uvicorn **sans** `--proxy-headers` ni `--forwarded-allow-ips`.
- `backend/src/workhub/interfaces/rest/auth.py:112` utilise `request.client.host`.
- `backend/src/workhub/iam/infrastructure/throttle.py:121-123` hache cette IP comme identifiant de limitation.
- Preuve live : **5 échecs avec 5 e-mails distincts via `http://localhost:8080` → `429`**, `retry_after_seconds: 900`.
- Le hash observé correspond à `172.26.0.4`, l'IP du conteneur Nginx :
  `sha256("ip\0"+"172.26.0.4") = 1217336fe6539befb025f7ddbe9b3069d44f76aa4fcd267094e456b55ffa42a0`.

**Impact**

Un attaquant anonyme peut verrouiller la connexion de **tous les utilisateurs passant par le frontend** pendant 15 minutes, et répéter l'opération.

**Recommandation**

- Configurer Uvicorn pour approuver **uniquement** le réseau exact du proxy :
  `--proxy-headers --forwarded-allow-ips=<ip-ou-cidr-nginx>`.
- Ne jamais utiliser `*`.
- Ajouter un test d'intégration derrière un proxy simulant `X-Forwarded-For`.
- Compléter par une limite de débit au niveau Nginx.
- Ne pas baser la limite uniquement sur l'IP du proxy ; conserver la clé compte et envisager compte+IP.

La doc reconnaît le problème (`docs/implementation/E1-iam.md:229-231`) mais il n'est pas corrigé.

### H-02 — Un jeton d'intégration reste valide après désactivation du propriétaire

**Preuve live**

```text
OWNER_DISABLED_TOKEN_STILL_VALID integration ['skills:read']
```

Le propriétaire a été désactivé en base, puis le jeton a été résolu avec succès.

**Code**

- `backend/src/workhub/iam/application/principal.py:40-50` : le chemin jeton ne charge pas `app_user`.
- `backend/src/workhub/iam/infrastructure/repositories.py:304-332` : `find_active_by_hash` vérifie le jeton et l'intégration, mais **pas** `app_user.is_active`.
- `docs/implementation/E1-iam.md:58` affirme à tort que le resolver « vérifie l'état du compte ».

**Impact**

- Un collaborateur désactivé conserve l'accès via ses intégrations.
- Une désactivation d'admin pour compromission ne coupe pas les agents.
- Les scopes restent actifs jusqu'à expiration ou révocation manuelle.

**Recommandation**

- Joindre `app_user` dans la requête jeton et exiger `is_active = true`.
- Retourner l'identité propriétaire, pas seulement l'intégration.
- Révoquer les intégrations lors d'une désactivation, ou au minimum les rejeter immédiatement.
- Ajouter un test d'intégration de non-régression.

### H-03 — Secrets par défaut acceptés et mode production non appliqué

**Preuves**

- `deploy/.env.example:12,15,16,21` : `change-me`, `change-me-owner`, `change-me-app`, `change-me-change-me-change-me-32chars`.
- `deploy/.env.example:23` : `WORKHUB_COOKIE_SECURE=false`.
- `backend/src/workhub/iam/infrastructure/config.py:17` : le secret est seulement validé par `min_length=32`.
- `backend/src/workhub/iam/infrastructure/config.py:25` : cookie sécurisé par défaut à `False`.
- `deploy/docker-compose.yml:4` : `WORKHUB_ENV` est défini.
- `WORKHUB_ENV` n'est **jamais lu** dans le code backend.
- La stack locale auditée tourne avec `--env-file .env.example`, donc avec ces secrets connus.
- Cookie live observé : `HttpOnly; Max-Age=2592000; Path=/api/v1/auth; SameSite=strict`, **sans `Secure`**.

**Impact**

- JWT forgeable si le secret par défaut est utilisé et qu'un UUID utilisateur est connu.
- PostgreSQL accessible localement avec un mot de passe superutilisateur public.
- Cookie de session transmissible en HTTP si le déploiement oublie `WORKHUB_COOKIE_SECURE=true`.
- Risque de copier `.env.example` en production, comme la documentation l'encourage.

**Recommandation**

- Refuser au démarrage les valeurs `change-me…` et les secrets connus.
- Exiger `WORKHUB_ENV=production` et appliquer alors `cookie_secure=true`, refus des placeholders et des mots de passe DB par défaut.
- Générer les secrets avec un script ou `openssl rand -base64 48`.
- Ne pas fournir de secret par défaut utilisable.
- Mettre à jour `docs/installation.md:51`, qui affirme déjà l'absence de secret par défaut.

### H-04 — Commit après réponse HTTP : succès mensonger en cas d'échec

**Code**

- `backend/src/workhub/iam/api.py:106-126` : `get_auth_service` fait `yield`, puis `commit()` dans le `else`.
- `backend/src/workhub/iam/api.py:129-149` : même schéma pour `get_integration_service`.
- `backend/src/workhub/iam/api.py:152-171` : même schéma pour `get_principal_resolver`.
- FastAPI `0.162.5`.

**Reproduction**

Avec un générateur de dépendance qui lève après `yield` — équivalent d'un échec de commit en teardown — sur le vrai endpoint de logout :

```text
LOGOUT_AFTER_TEARDOWN_FAILURE_STATUS 204 body_len 0
```

La réponse est **204 No Content**, alors que la transaction a échoué. Le log HTTP affiche même `status_code: 204`, niveau `info`.

**Impact**

- Un logout peut renvoyer 204 sans supprimer la session.
- Une révocation de jeton peut renvoyer 204 sans être persistée.
- Une création d'intégration peut renvoyer 201 sans exister réellement.
- Les contrôles de sécurité deviennent silencieusement inopérants.

**Recommandation**

- Déplacer le `commit()` **avant** le retour de la réponse, dans le service ou une unité de travail explicite.
- La dépendance ne doit faire que `close()`/`rollback()` en cas d'exception.
- Ajouter des tests d'injection de panne sur commit.
- `iam/api.py` n'est couvert qu'à **50 %**.

### H-05 — DoS non authentifié via Argon2 et limitation non atomique

**Preuves**

- `backend/src/workhub/iam/infrastructure/security.py:25-30` : Argon2id, `time_cost=3`, **`memory_cost=65536` (64 MiB)**, `parallelism=4`.
- Le login est public : `POST /api/v1/auth/login`.
- `backend/src/workhub/iam/application/auth.py:57-72` : `check()` puis `record_failure()` sont deux opérations distinctes.
- `backend/src/workhub/iam/infrastructure/throttle.py:52-68` : lecture du compteur.
- `backend/src/workhub/iam/infrastructure/throttle.py:70-108` : incrément séparé.
- Un burst concurrent peut dépasser la limite avant que les échecs soient enregistrés.
- `backend/src/workhub/iam/application/auth.py:72` : le succès appelle `reset()`, qui supprime la clé IP **et** la clé compte.
- `frontend/nginx.conf` n'a **aucun** `limit_req` ni `limit_conn`.
- `deploy/docker-compose.yml` n'a **aucune limite** mémoire/CPU/PIDs.
- Le verrou par compte est reconnu comme exposé au DoS ciblé (`docs/implementation/E1-iam.md:187`).

**Impact**

- Un attaquant non authentifié peut saturer le CPU/RAM avec des logins parallèles.
- Il peut verrouiller un compte connu.
- Il peut contourner la limite IP en réinitialisant avec un compte valide, puisque `reset()` supprime aussi la clé IP.
- Le proxy partagé aggrave le verrouillage (H-01).

**Recommandation**

- Limite de débit Nginx (`limit_req`) et connexions (`limit_conn`).
- Sémaphore de hachage et file d'attente bornée.
- Limites mémoire/CPU/PIDs Docker.
- Compteur atomique en base (`INSERT … ON CONFLICT … DO UPDATE`) ou verrou transactionnel.
- Clés compte et IP indépendantes ; le succès ne doit pas réinitialiser l'IP.
- Temporisation progressive, CAPTCHA ou preuve de travail si exposition publique.

## Constats Moyens

### M-01 — Cycle de vie des sessions et credentials incomplet

- Refresh token de **30 jours glissant** : `config.py:19`, `repositories.py:206-224`, `auth.py:88-92`.
- Pas de durée absolue, pas de détection de réutilisation, pas de révocation de famille.
- Le JWT d'accès reste valide jusqu'à **15 minutes après logout** : `config.py:18`.
- Pas de MFA, changement de mot de passe, récupération de mot de passe ni déverrouillage de compte.
- Pas d'inventaire des sessions ni de « révoquer toutes les sessions ».
- Les limites sont reconnues `docs/implementation/E1-iam.md:232-233`.

**Recommandation** : durée absolue, rotation avec détection de réutilisation, révocation globale, `jti` ou session liée, MFA admin, changement/réinitialisation de mot de passe, déverrouillage.

### M-02 — Audit des écritures d'intégration absent

- La DoD E1 exige **une ligne `audit_log` par écriture** : `docs/developpement.md:77-82`.
- Aucun port audit dans `IntegrationService`.
- `backend/src/workhub/iam/application/integrations.py` ne journalise aucune création/révocation.
- `audit_log` existe en base, avec trigger append-only et privilèges restreints, mais n'est pas alimenté par l'application.
- E1-08 est explicitement non fait : `docs/implementation/E1-iam.md:239`.
- Les logs HTTP ne contiennent ni principal, ni jeton, ni résultat métier.

**Recommandation** : implémenter E1-08 avant toute exposition ; écrire l'audit dans la même transaction que l'écriture métier ; acteur, `request_id`, résultat, cible, avant/après si nécessaire.

### M-03 — Autorisation par denylist, sans registre de scopes ni contexte propriétaire

- `backend/src/workhub/iam/domain/api_token.py:15-24` : validation syntaxique + **denylist de 4 scopes** seulement.
- Tout scope inconnu mais bien formé est accepté.
- Un porteur futur de `integrations:manage` pourrait émettre des scopes au-delà de ses propres droits.
- `Principal.id` d'un jeton est l'ID de l'intégration, pas celui du propriétaire.
- `backend/src/workhub/shared/domain/authorization.py:15-35` : `require_scope` est opt-in ; une route peut oublier de le déclarer.
- `backend/tests/contract` est vide : aucune vérification automatique que chaque route protégée déclare un scope.
- E1-06/E1-07 restent ouverts (`docs/implementation/E1-iam.md:236-237`).

**Recommandation** : registre central en allowlist, sous-ensemble des scopes du créateur, contexte owner/actor dans le principal, test d'inventaire des routes, refus par défaut.

### M-04 — Composition de production et privilèges DB non testés

- Les tests d'intégration utilisent les services directement, pas le câblage HTTP réel avec PostgreSQL.

- Aucun test des privilèges réels, de `audit_log` append-only ou de `db-grants`.
- Aucun smoke test Compose en CI.
- Aucun test de commit/rollback, de proxy, de désactivation propriétaire, de cookie de production.

**Recommandation** : tests ASGI + vraie DB avec `workhub_app`, tests de rôles, tests de composition `iam/api.py` (90 % minimum), smoke Compose, injection de panne transactionnelle.

### M-09 — Jetons d'intégration : expiration optionnelle, pas d'inventaire ni de purge

### M-10 — Défense en profondeur DB insuffisante

- `workhub_app` a le DML sur **toutes** les tables, y compris `app_user.password_hash`, `app_user.is_admin`, `session.refresh_token_sha256` et l'insertion dans `audit_log`.

- Pas de `pgaudit`, pas de chiffrement des backups.

**Recommandation** : moindre privilège/colonnes, RLS si multi-tenant, HMAC avec pepper pour les clés de limitation, rôle bootstrap séparé, `pgaudit`, backups chiffrés.

## Limites de l'audit

- Pas de test d'intrusion externe ni de test de charge.
- Pas de scan d'image, SBOM, SAST ou revue de code tiers.
- Pas d'environnement de production, de TLS/Caddy réel, ni de test de restauration.
- MCP, CLI et UI d'authentification absents ou squelettes : non testables fonctionnellement.
- Les documents PDF/ODT du projet n'ont pas été audités.
- Aucune injection SQL, XSS ou CSRF directe relevée dans le code revu, mais cela ne vaut pas garantie sans SAST/pentest.

## Conclusion

WorkHub a un **bon socle d'ingénierie** : séparation des modules, Argon2id, jetons hachés, isolation propriétaire, tests réels PostgreSQL, CI structurée, containers non-root et documentation honnête sur plusieurs limites.

Mais les **cinq constats élevés** interdisent une exposition publique en l'état. Les deux plus critiques sont la **désactivation propriétaire non appliquée aux jetons** et les **secrets de démonstration acceptés en production**. Le verrouillage proxy et le DoS Argon2 sont des problèmes de disponibilité immédiats.
